# 長い補足の会話とコンテキスト予算



2026-09-11 の上流の修正記録です。元の実装は、要求 JSON の文字数をトークン数として扱い、メインタスクの 32K の出力予約を継承していました。そのため、HTML、JavaScript、ツールの結果がコンテキストの多くを占める場合、有効な補足の質問を早すぎる段階で拒否していました。

<a id="open-source-implementations-reviewed"></a>
## 調査したオープンソース実装

- [Grok CLI の補足コンテキスト](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/agent/agent.ts#L739): 約 2000 文字の予算、1 メッセージ最大 400 文字で、最近のユーザー・アシスタントのテキストを抽出します。この経路は継続する補足の質問履歴を保持しません。
- [Grok CLI の独立した要求](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/utils/side-question.ts): 独立した中止シグナル、対応時は 2048 トークンの出力上限、ツールなし。
- [Grok CLI のメインセッション圧縮](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/agent/compaction.ts): トークンを推定し、最近の内容を保持し、古い要約を新資料で更新し、ターンをまたぐ切り詰めに対応します。
- [OpenCode のセッション圧縮](https://github.com/anomalyco/opencode/blob/b3f1a96c6dd7adeb28b36dd11add1998fc84d67b/packages/core/src/session/compaction.ts): 要求全体を推定し、出力・バッファーを予約し、最近の内容と更新式の要約を組み合わせ、ツールなしで要約を要求します。この実装の既定値は、最近のコンテキスト 8000 トークン、要約出力 4096 トークンです。
- [OpenCode の超過からの復旧](https://github.com/anomalyco/opencode/blob/b3f1a96c6dd7adeb28b36dd11add1998fc84d67b/packages/core/src/session/runner/llm.ts): アシスタントの出力開始前のみ復旧を試み、復旧した呼び出しは同じ復旧経路に再進入しません。

ARTEX は、出力予算の分離、最近の内容と更新式の要約、回数を制限した復旧を取り入れました。Grok のテキスト抜粋ではなく、norma v0.3.6 の構造化メッセージとツールの対を保持しました。OpenCode 方式のメインセッション圧縮イベントは、ARTEX のメイン会話記録には書き込みませんでした。ScopeWeaver はこの設計を保持します。参照バージョンは過去の実装を示します。

<a id="request-budget-and-execution"></a>
## 要求の予算と実行

- メッセージには、norma のコンテンツブロックの UTF-8 バイト推定に 4/3 の余裕を加え、システム指示、ツールスキーマ、メッセージラッパーの負荷を含めます。正確なモデルのトークン数ではなく、推定です。
- 補足の出力は既定で最大 8192 トークンとし、メイン設定の出力上限を超えません。`ARTEX_BTW_MAX_OUTPUT_TOKENS` は、サーバー側の上限を 256～32768 で受け付けます。既定モデルやメインタスクのパラメーターは変更しません。
- 入力予算は、コンテキストウィンドウから出力上限と安全余裕を引いた値です。不明なウィンドウには、プラットフォームの既定値 200K を使います。安全余裕はウィンドウの 5% で、128～8192 トークンに制限します。
- 成功したやり取りは、序数の昇順で最大 20 件ずつ読み込みます。元のやり取りを最大 20 件保持し、入力予算の 4 分の 1 または 16K トークンを超えません。
- 超過したやり取りは、履歴の出典とコンテキスト時刻を伴う更新式の要約に反映します。古いアシスタントの回答は新しいツールの証拠ではなく、矛盾する場合は最新のメインスナップショットを優先します。
- メインコンテキストがまだ長すぎる場合、コピー内の古いメッセージのみを要約します。最近の最大 8K トークンは残します。切断位置ではツールの呼び出しと結果の対を保持し、大きすぎるグループは全体を要約に入れます。
- 要約入力は、残りのウィンドウ容量に合わせて UTF-8 の安全な境界で分割し、出力は 2048 トークンに制限します。空、切り詰め、ツール呼び出し、予算超過の要約はキャッシュしません。補足の要求 1 件は、同じ 120 秒のタイムアウト内で要約呼び出しを最大 12 回行えます。上限では無限ループせず明示的に失敗します。
- テキスト・ツール呼び出しの出力前に起きた最初のモデルのコンテキスト超過エラーでは、小さい要求で 1 回再試行できます。推定サイズが減らなければ即座に復旧を停止します。その他のモデルエラーや部分的なストリームでは、この復旧を行いません。
- 要約、失敗した試行、中止を含め、返されたすべての使用量を同じ補足の要求に累積します。プロバイダーが使用量を返さなければ、記録できるのは 0 のみです。推定を測定済みの使用量と偽ってはいけません。

<a id="persistence-and-interface"></a>
## 永続化と画面

`side_question_sessions.memory` は、古いやり取りの要約、対象の序数、スナップショットの識別情報でキャッシュしたメインコンテキストの要約を保存します。`side_question_requests.context_info` は、準備段階、実際の再生件数、要約の使用、予算の推定を保存します。

要約を保存するのは、元の要求が実行中で、消去バージョンが一致する場合のみです。消去はキャッシュも削除し、遅い書き込みでデータが戻ることはありません。新しいスナップショットは古い要約を再利用しません。アーカイブ v3 は要約フィールドを保持し、これらがない古い v3 の復元では空のオブジェクトを設定します。v1/v2 も互換性を保持します。

POST はバックグラウンドの準備・圧縮前に要求を受理して返し、その処理中は受け入れロックや DB トランザクションを保持しません。SSE・履歴は、準備、やり取りの整理、コピーの圧縮、回答の段階を表示します。圧縮失敗は補足の要求の最終失敗として保存します。フロントエンドは、入力欄にトーストを重ねずエラーを保持し、失敗した質問を下書きに戻します。履歴のポーリングは送信エラーを消去しなくなりました。
